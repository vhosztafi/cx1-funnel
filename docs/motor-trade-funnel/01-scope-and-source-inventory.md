# Motor Trade Funnel Scope and Source Inventory

> This specification is derived from repository code only. The repository is read-only evidence for this exercise: no legacy application source is changed, and no live funnel, environment value, or browser/session state is used to create requirements.

## Evidence Authority and Status

`CleggGifford.CoverX.UI/` is the controlling authority for observable front-end behaviour under decision D-01. A supporting repository dependency may be followed only when a mounted React consumer needs it to resolve a front-end-visible fact such as a displayed option, validation constraint, default, derived value, route, or persisted state (D-02). Supporting API, domain, mock, or legacy sources may fill a fact that React leaves open, but they cannot override explicit React behaviour (D-03). If supporting evidence disagrees with React, preserve the React behaviour, mark the fact as a conflict, and link a clarification entry instead of merging the two accounts (D-04).

Every material fact must have exactly one of these evidence statuses:

| Evidence status | Meaning and required treatment |
|---|---|
| `Direct React` | Mounted React code, an imported static asset, or mounted styling directly defines the observable fact. This is controlling evidence. |
| `Dependency-resolved` | React proves that the fact is consumed, and a bounded traversal to another repository source supplies the missing front-end-visible value or rule. |
| `Conflict` | Supporting repository evidence disagrees with explicit React behaviour. Retain the React behaviour and link a clarification entry. |
| `Unresolved` | A completed repository-only trail ends without the required value or leaves ambiguous React composition. Link a clarification entry and continue unaffected work. |

Per D-05, each material fact row must contain:

- a stable fact ID;
- exactly one evidence status from the table above;
- a repository-relative `path:symbol` evidence reference; and
- an optional clarification ID when the fact is `Conflict` or `Unresolved`.

Traversal starts at a mounted React consumer and continues only while an import, call, or stored value determines observable text, options, conditions, validation, routing, or state. It stops at transport-only, quotation-only, payment-only, generated, database/runtime-only, or unrelated behaviour. Unknowns are recorded in [clarifications.md](clarifications.md) and never block unrelated specification work.

## In Scope

- The complete observable root page mounted at `/`, including its product controls, exact ordering, links, styling evidence, interactions, and code-evidenced variants.
- The Motor Trade root control and its navigation into the Motor Trade road-risks sales funnel.
- The Motor Trade front-end journey from its root entry through the final pre-quotation sales step.
- Mounted React sources and bounded supporting repository dependencies that determine front-end-visible facts.
- The final in-scope component and the precise first excluded edge.
- Repository-traceable uncertainties and conflicts recorded as non-blocking clarifications.

## Out of Scope

- Commercial Combined beyond its root-page link and the point at which navigation begins.
- API and backend contracts or behaviour.
- Quotation generation and quotation results.
- Checkout and payments.
- Changes to any legacy application code.
- Live-funnel, live-environment, browser, database, or session validation.
- UX, content, architecture, or business-rule improvements or redesign.
- Implementation of a configurable XML/JSON funnel engine or other reusable funnel implementation.

The future Next.js, Tailwind CSS, and UI-kit stack is implementation context only. It does not change the as-is evidence or authorise behavioural reinterpretation.

## Phase 1 Depth Guard

Phase 1 inventories the evidence surface and establishes the hard entry and terminal boundaries. It may identify mounted step, navigation, state, validation, content, and data-source files so later work can find them, but it must not collapse later phases into this inventory.

- Phase 2 owns the full ordered step sequence, transitions, branches, navigation controls, progress behaviour, and state semantics.
- Phase 3 owns detailed question wording, answer options and values, visible supporting copy, required/optional states, conditions, validation, error messages, and derived or formatted values.
- Phase 4 owns final traceability, clarification disposition, and behaviour-neutral LLM handoff packaging.

The only Phase 1 behavioural detail recorded beyond inventory depth is what is necessary to make the complete root entry and the last-included-node/first-excluded-edge boundaries unambiguous.

## Bounded Dependency Traversal

The D-16 traversal rule is mandatory for every supporting-source claim:

1. **Start at a mounted React consumer.** Name the component, hook, store, or route that visibly consumes the fact. An unimported file or a product-shaped directory name is not a valid starting point.
2. **Follow behavior-bearing edges only.** Continue through imports, function calls, mappings, and persisted values while they determine visible text, option labels/values/order, conditions, front-end validation/messages, routing, or stored state.
3. **Preserve React authority.** A supporting source can fill a React-visible gap but cannot replace or reinterpret explicit React behavior. Any disagreement is a `Conflict` clarification while the React behavior remains controlling.
4. **Stop at the first non-behavior-bearing boundary.** Stop before transport contracts, quotation/rating/results, referral detail, checkout/payment, generated integration code, runtime/session/live values, database rows absent from the repository, or unrelated product/application behavior.
5. **Record the stop.** Keep any repository-resident shape, transform, ordering, or configuration already proved; mark the missing value `Unresolved` and link its clarification rather than guessing or blocking unrelated extraction.

### Dynamic-option traversal and stopping point

The concrete bounded trail is:

`CleggGifford.CoverX.UI/src/containers/dataContainer.tsx:DataContainer` (mounted React consumer) → `CleggGifford.CoverX.UI/src/api/motorTrade.ts:getMotorTradeOptions` (provider locator) → `CleggGifford.CoverX/CgLloyds20.WebApi/ApiControllers/FunnelMotortradeRoadRisksController.cs:Options` (assembly/transforms) → `CleggGifford.CoverX/CgLloyds20.WebApi/ViewModels/Api/MotortradeRoadRisks/MotortradeRoadRisksOptionsResult.cs:MotortradeRoadRisksOptionsResult` and representative producers `CleggGifford.CoverX/Cglloyds20.IP.MotortradeRoadRisks/DataService/LkIpMotortradeRoadRisksCompanyTypeDS.cs:ListAll` and `CleggGifford.CoverX/Cglloyds20.IP.MotortradeRoadRisks/DataService/LkIpMotortradeRoadRisksEuropeanAreaDS.cs:ListAll` (shape/configuration and database-backed source boundary, not exhaustive row-value sources).

Repository code proves the option property schema, selected DTO fields, mappings, ordering transforms, hard-coded configuration where present, and that `ListAll()` reaches persistence. It does **not** prove the current database-backed option rows when their IDs and labels are absent from repository files. Those row values stop at CLR-001 as `Unresolved` and remain non-blocking. This trail is not permission to document the endpoint contract, expand the detailed questionnaire in Phase 1, access a database/live environment, or infer values from model names.
