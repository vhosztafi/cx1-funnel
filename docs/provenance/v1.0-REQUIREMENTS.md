# Requirements: CX1 Motor Trade Funnel Specification

**Defined:** 2026-08-25
**Core Value:** Every observable motor-trade funnel behavior and business rule is captured accurately, completely, and traceably from the legacy source code.

## v1 Requirements

### Scope and Discovery

- [x] **SCOP-01**: Specification identifies the Motor Trade entry on the root page and records its observable entry behavior
- [x] **SCOP-02**: Specification identifies Commercial Combined on the root page but clearly excludes its funnel from further analysis
- [x] **SCOP-03**: Specification identifies the source files, components, routes, and front-end data sources that define the Motor Trade journey
- [x] **SCOP-04**: Specification defines the terminal pre-quotation step and excludes quotation, checkout, payment, API-contract, and backend behavior

### Journey Structure

- [x] **JOUR-01**: Specification lists every Motor Trade step in implemented order, from root-page entry through the final pre-quotation step
- [x] **JOUR-02**: Every step has a stable identifier, purpose, entry conditions, displayed content, collected answers, and possible exits
- [x] **JOUR-03**: Specification captures every transition, branch, skipped step, and dependency on earlier answers

### Questions and Content

- [x] **QUES-01**: Every question is documented with its exact visible wording, field or control type, required or optional state, and position
- [x] **QUES-02**: Every answer option is documented with its exact label, underlying value when present, ordering, grouping, and default state
- [x] **QUES-03**: Every heading, instruction, help message, hint, disclaimer, and other relevant user-visible copy is captured exactly as represented in code
- [x] **QUES-04**: Dynamically sourced front-end options are resolved from repository data where possible and otherwise entered in the clarification log

### Business Rules and Validation

- [x] **RULE-01**: Specification captures all conditional visibility, enablement, branching, and skip rules with their precise triggering conditions
- [x] **RULE-02**: Specification captures required-field rules, allowed values, length or range constraints, format checks, and cross-field validation
- [x] **RULE-03**: Specification captures exact validation and error messages and when each appears
- [x] **RULE-04**: Specification captures calculated, derived, normalized, or formatted values and their dependencies where evidenced by front-end code
- [x] **RULE-05**: Specification distinguishes explicit code behavior from inferred or unresolved behavior

### Navigation and State

- [x] **NAV-01**: Every step documents Back, Continue, and other navigation controls, including enabled or disabled conditions
- [x] **NAV-02**: Specification captures progress indicators, displayed step numbering, and any divergence between visible and internal step order
- [x] **NAV-03**: Specification captures answer retention, reset, or loss when users navigate backward, forward, or across conditional branches where evidenced by code
- [x] **NAV-04**: Specification documents the final pre-quotation action without extending into quotation or API behavior

### Evidence and Uncertainties

- [x] **EVID-01**: Every material behavior or business-rule claim includes a traceable source-file or symbol reference
- [x] **EVID-02**: A clarification log records each missing, ambiguous, conflicting, or dynamically unavailable detail
- [x] **EVID-03**: Every clarification entry states the affected step or rule, available evidence, implementation impact, and question requiring resolution
- [x] **EVID-04**: Unresolved clarification entries do not prevent completion of unaffected specification sections

### LLM Implementation Handoff

- [x] **HAND-01**: Final Markdown is structured so an LLM can implement each step, question, option, rule, and transition without rediscovering legacy behavior
- [x] **HAND-02**: Instructions identify Next.js, Tailwind CSS, and a UI kit as the future implementation context without changing documented behavior
- [x] **HAND-03**: Implementation guidance clearly separates mandatory legacy behavior from behavior-neutral engineering guidance
- [x] **HAND-04**: The final specification contains no proposed UX, content, business-rule, or architectural improvements

## v2 Requirements

No deferred requirements are currently defined. Any future migration or implementation scope must be established separately from this as-is specification milestone.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Commercial Combined funnel | Only the Motor Trade journey is included; Commercial Combined is retained solely as root-page context |
| API and backend contracts | Source may supply front-end facts, but backend behavior is not part of this specification |
| Quotation and quote-result behavior | The documented journey ends at the final pre-quotation sales step |
| Checkout and payments | Occur beyond the agreed front-end funnel boundary |
| Legacy code changes | This project produces documentation only |
| Live-environment validation | Repository code is the sole source of truth |
| UX, content, or business-rule improvements | Existing behavior must be captured exactly as implemented |
| Configurable XML or JSON funnel engine | This is a possible future implementation direction, not part of the as-is specification |

## Definition of Done

- Every v1 requirement is mapped to exactly one roadmap phase and has verifiable completion evidence
- The complete Motor Trade journey is documented from root-page entry to the final pre-quotation step
- All material specification claims are traceable to repository code
- All unresolved details appear in the clarification log and do not obscure confirmed behavior
- The final Markdown is usable as an LLM implementation handoff without introducing behavioral changes
